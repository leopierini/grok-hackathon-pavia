## Behavior

An acknowledgement is bound to the issued `command_id`. `accepted` stays non-terminal. `running` is not completion. `completed`, `rejected`, `cancelled`, `failed`, and `unknown` are terminal. `observed_motion` and `verified` are stored as reported.

A completed `track_step` can remain airborne. It is not landing proof, including when `observed_motion` is `grounded`. The only grounded record is a `land` command that is `completed`, `verified` true, and `observed_motion` `grounded`. `is_flying` in the ack detail, or `is_flying` on an observation, is ignored. A drone observation's `flight_state` is not landing proof. A stale observation is ignored.

A reply deadline that passes with no terminal ack emits one `query_command` for the original `command_id` and leaves the command unresolved. A second expiry does not emit another query. No new command id, takeoff, move, or power cycle is proposed. A later ack for that same id can still resolve it.

The same final payload is idempotent and does not emit a second `operation_completed`. A different final state, or the same message id with a different payload, is an `unsafe_state` fault and does not replace the stored state. A lower sequence is stale. A foreign epoch is `epoch_mismatch`. A dog `command.ack` is rejected for Task 24. Unknown landing sets `recovery_required`, blocks the next mission, and is not cleared by a later completion or by the demo goal.

Proposed events are `state_changed`, `operation_completed`, `operation_failed`, and `recovery_required`. The workflow still has to apply them through `StatePort`.

## Extra edge cases

- A duplicate final payload with a new message id does not emit a second completion.
- Reusing one message id with a different payload is a conflict and keeps the earlier state.
- `running` followed by `accepted` conflicts.
- `rejected`, `cancelled`, and `failed` are terminal and are not verified completion.
- A lower sequence does not rewrite the record.
- Correlation or mission mismatch is `contract_mismatch` and does not bind the command.
- A string such as `"true"` is rejected for `verified`. A boolean deadline is rejected.
- After one query, the original completed ack still closes that same command id.
- Expiring one command does not query a second registered command.
- A fresh observation that says `grounded` or `is_flying: false` does not ground an airborne track step.
- A stale observation cannot clear unknown landing.
- Unknown execution on a track step requires recovery and does not by itself block the next mission.
- A verified `land` with `observed_motion` `grounded` is the grounded case. Stationary or unverified landing is not.
- A stale ticket is rejected and no device method is called.
