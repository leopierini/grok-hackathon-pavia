## Behavior

A dog step is stopped only when the ack state is `completed`, `verified` is true, and `observed_motion` is `stationary`. `accepted` alone is not stopped. `completed` with `verified` false is not stopped and leaves the command active.

`rejected` with `reason_code` `expired_command` records `motion_occurred` false and clears the active-command flag. The same reason with `moving` or `airborne` faults and still records no motion.

A timeout is measured on the manual clock as `lease_ms` from the moment the command is bound. It sets `query_command` to that same command id. It does not create `cmd-dog-002` or any other `dog.command`. A second timeout for the same command emits no extra event.

Acks bind to the issued `command_id`. The ack `correlation_id` must be the command `message_id`. A foreign command id, mission, or epoch is rejected and does not bind. A repeated `command_id` with a different command `message_id` is refused and does not restart motion. Duplicate terminal facts are idempotent. A different terminal state, or the same state with different verified/motion/reason facts, faults with `unsafe_state` and `recovery_required`.

While any command is `running`, or any record is faulted, `block_next_step` is true. That is data for Task 22. This package does not import Task 22.

A halt ack is a separate command id. Completing `cmd-dog-halt-001` does not mark `cmd-dog-001` completed and does not clear a halt. `halt_cleared`, `demo_goal_reached`, `target_arrival`, and `motion_allowed` stay false. `commands_issued` stays 0.

A LiDAR or obstacle `reason_code` can still be a verified stationary stop. `stop_cause` is `lidar`, which is not target arrival and not the demo goal.

A readiness object, or a `dog.observation` with `stationary`, is applied only at or after the lease, or when `observed_after_window` is true. If it says the dog is not stationary, a previous stop is withdrawn and no new move is proposed.

A latched cancellation rejects a direct request even when the ticket is omitted. A current ticket whose kernel epoch does not match is rejected by Task 01. The v2 message epoch is compared with the command message, not with that kernel epoch. The examples use message epoch 1 and the kernel starts at epoch 0.

## Message kinds

Accepted from the copied examples:

- `dog.command` — `ground-to-dog-command.json`, `ground-to-dog-halt.json`, and the task fixture `expired-dog-command.json`
- `command.ack` — `dog-ack-accepted.json`, `dog-ack-running.json`, `dog-ack-completed.json`, `dog-command-rejected.json`

Rejected on purpose:

- a drone-sourced ack
- `verified` sent as the string `"true"`
- `halt_latched` sent as the string `"true"`
- an ack whose `correlation_id` is not the command `message_id`
- an ack epoch, mission, or `command_id` that does not match the issued command
- `expired_command` combined with `observed_motion` `moving`

## Extra edge cases

- A stale epoch does not bind, so a later matching ack can still be tracked.
- A lower `seq` does not rewrite a verified stop.
- A readiness reading before the lease does not remove a stop. The same reading after the lease does, and it still proposes no command.
- A current kernel ticket can carry a message whose epoch is 1.
- After cancellation, the earlier `accepted` state remains and `halt_cleared` stays false.
- Replaying the completed example adds no event. `terminal_events` stays 1 and `event_count` stays 3 for the accepted, running, and completed sequence.

## Limitations

- This machine has CPython 3.12.10 only. Mypy checks with `python_version = 3.11`. A 3.11 interpreter was not executed.
- `python -m patrol.ground.sim --task 24` cannot load this manifest until Gate C registers the v2 schema and slot. The harness test is the simulation evidence for these cases.
- The manual clock is not aligned with the example timestamps on 2026-11-04. The command window is `lease_ms` from bind time. `expires_at` is validated as a timestamp and is not compared with `utc_now()`.
- A request with no ticket is accepted when cancellation is not latched. It still cannot authorize motion.
- An `accepted` command sets `active_command` but `block_next_step` becomes true only for `running` or a fault. Callers that must hold selection during `accepted` should also read `active_command`.
- A LiDAR stop that is verified and stationary is still `stopped`. The distinction is `stop_cause=lidar` and `target_arrival=false`, not an inferred arrival.
- Nothing here measures Go2 motion, lease expiry on the robot, or link-loss delivery. The dog app still owns the local stop.
