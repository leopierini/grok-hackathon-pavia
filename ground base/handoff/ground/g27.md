## Behavior

A reached goal and a landing result are stored in one recovery record and decided separately. The goal fixture is copied. Distances are not recomputed.

Landing is `verified` only when all of these are true: a land command was issued, the acknowledgement `command_id` is that land command, `state` is `completed`, `verified` is boolean true, `observed_motion` is `grounded`, and the latest drone observation `flight_state` is `grounded`.

`state` `unknown` sets `landing_unverified` and `device_recovery_required`. The goal event's own `device_recovery_required: false`, its timestamp, and a picture on the observation do not clear that fault. `flight_state` `airborne` after a completed land acknowledgement is a contradiction and stays a fault. A failed, rejected, or cancelled land acknowledgement is a fault. The goal record stays.

If no land command was issued, landing status is `not_attempted`. A grounded observation or a finished track step does not turn that into a landing. The dog recommendation on every result is `hold_stop`. `issued_commands` and `search_commands` stay empty. Device doubles are not called.

The same goal event id and land command id replay to one record. Clearing a latched recovery without a new grounded observation is rejected. A later evaluation clears that one record when the observation id is new, `flight_state` is `grounded`, and the land acknowledgement is verified grounded. `attempt_clear` uses the same rule. The record id stays the same. `software_retrieved` stays false.

## Extra edge cases

- Boolean text such as `"true"` for `verified` is rejected. It is not treated as true.
- A `running` land acknowledgement is not a verified landing. `accepted` uses that same incomplete path and does not have its own test.
- A failed land acknowledgement keeps the goal and sets recovery.
- An acknowledgement for another command id does not verify the land command.
- A goal that arrives after an unknown landing is recorded and does not clear the fault. Replaying the same observation id does not clear it either.
- A new grounded observation plus a verified land acknowledgement clears that one record, including when the caller does not set `attempt_clear`. The same observation id does not. Physical retrieval stays an operator step.
- Goal and land messages from different missions are rejected. Different epochs fail the same check and do not have a separate test.
- `event-landing_unverified.json` parses and is not treated as `demo_goal_reached`.
- Clearing when nothing is latched is rejected.
- The journal double's record list stays empty. No search, move, or `land` call is added to the device trace.

## Limitations

- Nothing here measures a Tello landing or proves the aircraft is on the ground. `flight_state` and the acknowledgement are inputs. An operator still has to retrieve the aircraft.
- This task checks the fields it branches on. It is not the full 2.0-draft envelope validator. That belongs to Task 11.
- With no land command, status stays `not_attempted` even if the observation says the aircraft is airborne. That is not turned into a landing fault here.
- A latched unknown landing stays latched until a new observation id says `flight_state` `grounded` and the land acknowledgement is verified grounded. A later picture, a repeated goal event, or `attempt_clear` without that new observation does not clear it.
- `test_live_command_refuses_without_providers` already failed on this baseline before this task: it expects the text `base.safety` inside the missing-provider list, and `base.safety` is already installed by Task 10. This change does not rewrite that test. Discovery of the v2 manifest now succeeds, so the live command still fails on missing providers rather than `schema_mismatch`.
- Tasks 04 and 06 are not in the merged baseline used here.
