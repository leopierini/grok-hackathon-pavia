## Behavior

`ConfigPort.load` reads UTF-8 JSON through the kernel IO seam, rejects duplicate keys, non-finite numbers, booleans used as numbers, and unknown ground keys without echoing their values. Relative paths resolve from the file that declares them. Route and profile files are checked as files and are not parsed. Ethernet is the default dog transport. A Wi-Fi profile can be configured beside it and does not change adapter modes or grant acceptance. Tello's radio is `wifi` and the recorded SDK string is `DJITelloPy`; the module is not imported. A missing battery reserve, a missing drone file in fake mode, or a fake drone mode leaves flight disabled. Real pad launch with a fake dog is rejected. Empty fake input uses `blocked_resolved` and does not read `XAI_API_KEY`. Caller `scenario` overrides the file. The redacted view replaces adapter configs with `redacted` and adds only safe capability flags.

## Extra edge cases

- Duplicate JSON keys, NaN, Infinity, and `1e309` are rejected.
- An empty string path is not the fake default.
- Non-UTF-8 input and files over 256 KiB are rejected.
- Fake adapters that name different scenarios are rejected when the caller does not override them.
- A dog file cannot set `dog_transport`. `connection_mode` value `ethernet` is not a vendor mode and is not copied into the transport field.
- The selected `dog_config_path` must match `dog_profile_paths` for the active transport.
- `profile_identity` cannot contain a collected credential. Error text is scrubbed.
- Mutating the caller's mode dict after `load` does not change the returned settings. Returned mappings and lists are immutable; lists become tuples.
- A zone list that omits `room_2` must supply `profile_by_zone`.
- Source files are not rewritten and no `.partial` file is created.
- Floor launch may name a real drone with a fake dog. Carried and stationary pad may not.

- Nothing here is physical evidence. Ethernet, Wi-Fi, the router, and Tello were not exercised.
