## Behavior

One seeded command replays an ordered drone-first scenario from task-owned fixtures. The happy path on seed 0 is: capabilities, stable hold, drone detection, one approved drone step while the dog stays stopped, beacon epoch 4, one valid Pi window, one safe dog step, dog-camera handoff, proximity goal, then a separate verified landing. Device doubles are not called. Model proposals stay addressed to Ground. There is no RSSI-to-meters field and no second takeoff after a timeout.

`controlled_motion: false` ends in `supervised_stop`. A stale frame, a blocked planner, and a noisy RSSI window stop before an invented dog step. Unknown landing after a reached goal fails only the landing assertion. `example-events.jsonl` is rejected as one mission (`window_before_epoch_advance`, `dog_moved_during_drone`, `ack_without_command`). A real-mode flag or a non-boolean `simulated` value is rejected before any step. A second publish into the same run directory is rejected and the first report stays. Two run ids create two directories.

`demo/script.md` is the two-minute operator brief: site check, 4 m only when the venue allows it, arm, drone verification, what the dog app receives, halt, goal versus landing, the contract files for each teammate, and the live log path `artifacts/<mission_id>/events.jsonl`. It states that this rehearsal is not physical acceptance.

The contract copies under `fixtures/ground/g32/messages/` keep the example beacon epoch 3. The ordered dog command and Pi window use beacon epoch 4, because that is the epoch the drone command advances to. The verified land acknowledgement is a task-owned message; the catalog's landing example is the unknown-landing failure.

## Extra edge cases

- A string `"true"` for `simulated` is rejected. It is not coerced to true.
- Median RSSI `0` with an empty sample list is a sentinel failure, not a distance.
- A payload key `rssi_m` fails the rehearsal.
- Replaying the happy playlist with the dog command still on beacon epoch 3 fails `stale_beacon` and does not emit `dog_step`.
- A request payload `scenario` selects the case when the harness name is not a barrier or real-mode flag.
- The first overwrite report remains the happy-path report. The command result is `overwrite_rejected`.
- Cancelling the barrier worker before release makes simulator teardown fail `assert_released`. That case is not in `--case all`, so the official command stays green. `barrier_release` is in `--case all` and passes after the harness releases the barrier.
