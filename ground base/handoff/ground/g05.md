## Behavior

`run` checks the ticket, latch, mission deadline, and stage budget before calling the factory. A zero or already expired budget returns `timeout` / `expired_deadline` with no factory call. The stage `RunContext` uses the mission cancellation event and `min(mission deadline, now + stage limit)` on the injected clock. A second `bind_mission` cannot move that deadline later.

After the awaitable finishes, halt wins over a returned value. If halt is clear and the injected clock is at or past the deadline, the status is `timeout`, including exact equality. `CancelledError` is `cancelled`, not `completed`. A returned value stays on the result either way and `authorizes_next` stays false.

Timeout or halt cancels the task, but a task that keeps running stays in `pending()` and in the kernel registry. Another `run`, including recovery, is rejected with `unsafe_state` until that task finishes. `safety.reset` on the kernel double also stays blocked while the kernel registry is pending. The error text says coroutine cancellation does not prove the device stopped.

`run_recovery` uses a new `threading.Event` and its own budget. It does not read the cancelled mission context and does not change the stored mission deadline. Ordinary `run` after halt still does not start. `run_cleanup` keeps the original `OperationResult` object when cleanup raises; the cleanup error is appended to `cleanup_errors`.

Nothing here retries walking, turning, takeoff, or inspection. A later call after the mission deadline is another rejection, not a second factory invocation.

## Extra edge cases

- `limit_s` of `0` is an expired budget. Negative, non-finite, and boolean limits are `invalid_input`. None of them call the factory.
- A factory that returns `None` is `completed`. A factory that returns a plain string is `invalid_input` after that one call.
- `AdapterError` becomes `failed` / `unavailable` and keeps the adapter detail.
- A ticket whose epoch was replaced by `reset_generation` is `stale_ticket` and does not start.
- A 30-second manual deadline returns without a wall-clock sleep (`elapsed < 0.5`).
- Halt, then a value of `"late"`, stays `cancelled`. `inspect_late` can read a still-running task afterward without changing the recorded status.
- Pending resistant work blocks replacement and `safety.reset`. After the barrier is released and the task finishes, reset is allowed.
- Cleanup `RuntimeError("disk full")` is stored separately. The primary timeout object is the object returned to the caller.
- Peer safety, workflow, and executor doubles record no calls.

## Limitations

- This machine ran CPython 3.12.10. Mypy used `python_version = 3.11`, but Python 3.11 itself was not executed.
- The cancel waiter polls (`sleep(0)` on a manual clock, `0.01` s on a real clock). The kernel has no async cancellation subscription. The poll is only active while an operation is being observed.
- `pending()` is this executor's view of its own tasks. Quiescence for reset also depends on the kernel registry, which Task 01 does not prune. This executor does not add a `workers_idle` robot API.
- Recovery is allowed after halt only when nothing is still pending. It is not a motion retry and it does not clear the latch.
- No physical stop, landing, or network behavior was measured.
