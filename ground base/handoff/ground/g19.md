## Behavior

Dog motion is allowed only when the beacon `hold_state` is `stable`, `flight_state` is `airborne`, the manual clock is still inside `hold_valid_until` (the end instant is included), the BSSID matches the armed drone, and no search or track command is in progress. A completed `search_step` or `track_step` requires the next observation to carry a higher `beacon_epoch` before any window may be compared. Windows from the previous epoch stay in the result, labeled `invalid` and `retained`. A hover whose fixture says `beacon_moved` is false keeps the observation epoch even when the hover command cites epoch 4. The example `dog_dispatched` record is legal only while `dispatch_allowed` is true. This feature does not emit that event and does not build a dog command.

Message kinds consumed: `drone.observation`, `drone.command` (`track_step`, `search_step`, `hover`, `takeoff`, `land`). Message kind proposed: `state_changed` / `beacon_hold`. The copied `mission.event` `dog_dispatched` is a gate check, not an output.

## Extra edge cases

- The instant `hold_valid_until` is still inside the window. One second later the dog is blocked even though the label is still `stable`.
- A second identical observation returns the same decision and does not bump the epoch.
- `hold_state` `unknown`, `flight_state` `grounded`, and `flight_state` `unknown` all block. Unknown flight leaves the reported hold as `stable`.
- A running or accepted `search_step` / `track_step` forces `hold_state` to `moving` and suspends windows. A running `land` or `takeoff` forces `unknown` and does not advance the epoch.
- A running hover does not force `moving` and can keep epoch 3.
- A hover with `beacon_moved` true waits for epoch 4, same as a completed track step.
- An observation still on epoch 2 or 3 after a completed track to epoch 4 stays incomparable. The old window is `invalid` and retained. A window already tagged 4 is retained and `withheld` until the observation itself reaches 4.
- BSSID mismatch is `blocked` / `rejected`. Hex case does not matter. A different SSID with the same BSSID is accepted.
- `"false"`, `true` used as an epoch, `STABLE`, an inverted hold window, a missing armed BSSID, and a `move_local` action are `invalid_input`.
- `active_command_id` without a command description blocks. An explicit `drone_command_running: false` does not.
- RSSI numbers on a window are ignored. Loud and quiet samples produce the same decision.
- No journal write and no adapter call. The workflow would apply the proposed event.

## Limitations

- The v1 loader rejects this manifest. Slot registration is the senior's Gate C edit. Until then the packaged `sim` command and the full extension scan fail closed.
- The manual clock starts at 2026-01-01, so the example hold that ends at 2026-11-04T13:00:12Z is not expired until a test advances the clock.
- Nothing here measures a Tello beacon, laptop Wi-Fi, or a Go2 step. The policy does not read RSSI and does not issue the dog command a hold would allow.
- `dog_dispatched` is not produced. Callers must check `dispatch_allowed` before that mission event is legal.
- A completed land does not by itself advance the beacon epoch. Grounded or unknown flight still blocks the dog.
