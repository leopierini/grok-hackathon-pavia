## Behavior

The goal is reached only when the current track matches and both checks are fresh, inside the profile thresholds, with the dog stationary and the beacon hold stable.

Dog range and drone horizontal offset stay separate fields. A single 3D distance cannot satisfy both. At a fixture height of 4 m, a claim of 1 m full-3D proximity to a person's center is rejected. The standing-person center used for that geometry check defaults to 1 m when the caller does not supply one. A 4 m height with no 3D claim does not block a valid horizontal check.

Automatic dog sources are `lidar_associated` and `depth`, and they require `association_valid`. The automatic drone source is `calibrated_projection`. Operator sources count only when the profile sets `operator_evidence` and `operator_confirmed` is true on both sides. A missing number can be covered by that pair. A number that is present must still sit at or under the profile threshold. The 1.5 m values inside the example message are not the rule; `profile-open.json` supplies 1.5 m for the example, and `profile-tight.json` shows 1.2 m failing a 1.0 m dog threshold.

Obstacle clearance written into `range_m` is rejected. RSSI is rejected as a range. A person detection stays unresolved. Evidence older than 3000 ms is stale. An age of exactly 3000 ms is still current. A future timestamp stays unresolved. A string such as `"true"` is not a boolean.

The goal log uses phase `proximity_verify`, outcome `completed`, and `device_recovery_required: false`. That boolean is the contract example's statement that landing is a different record. This feature does not call `state.apply`, does not write the journal, and does not propose `drone.land` or any other device call. `flight_state` is absent.

Thresholds actually used are the first trace field, for example `thresholds:1.5,1.5`.

## Extra edge cases

- Exactly 3000 ms is still fresh. 3001 ms is stale. A timestamp after the evaluation instant is unresolved.
- Dog range equal to the profile maximum passes. A larger range stays unresolved even when the example message says 1.5 m.
- Null profile thresholds stay unresolved. The feature does not invent 1.5 m.
- Operator confirmation with both distances null succeeds only when the profile allows it and both sources are `operator`. One operator side beside a lidar range stays unresolved.
- Lidar plus a calibrated projection succeeds while operator evidence is disabled.
- A 4 m height without a 3D claim can still reach the goal.
- `"true"` does not count as a stopped dog.
- A latched cancellation emits no goal and does not set a landing recovery flag.
- An unassociated lidar range stays unresolved. The same number labeled as obstacle clearance is rejected.
- A different track id stays unresolved.

## Limitations

That test was not edited.
- The published goal example uses `seq` 11 and `sent_at` one second after the evidence. This feature proposes `seq` = evidence seq + 1 (9 for the copied example) and stamps `sent_at` with the evaluation time. The event name, phase, outcome, reason, and track match the example.
- The 1 m person-center height is an assumption for the impossible-3D check, not a measured body height.
- Nothing here measures lidar, a calibrated image projection, or a real operator confirmation. Ordinary tests use no robot motion.
- The v1 session snapshot is not given a `goal_reached` field. The proposal is the event payload; the workflow would apply it after its own ticket and cancellation checks.
