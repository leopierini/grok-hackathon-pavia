## Behavior

A `vision.decision` is accepted only when its `request_id` and `frame_id` match the outstanding `vision.request`, the decision arrives at or before that request's `expires_at`, and the request camera epoch is still current. `target_state` is `person_visible`, `not_visible`, or `uncertain`. The only detection label is `person`. Boxes are four normalized values with `xmin < xmax` and `ymin < ymax`.

The first accepted `drone_search` person opens `target-001` when the detection has no track id. A track id already on the detection is reused. A dog frame may update that same id. A different dog track id leaves the current track in place. `uncertain`, `not_visible`, and two people without a staged association produce review or hold and no proposal.

A stored `motion.proposal` is data on the result. Its payload uses the example proposal keys, `direction_hint` is the image direction, and it has no `motion`, `command_id`, or `sdk_command`. Destination is `ground`. An uncalibrated body-frame action becomes a hold proposal. A latched halt suppresses the proposal and does not clear the latch. Device ports are not called.

Confidence is stored as `model_score`. It is not a probability and not permission. `motion_authorized` stays false. The placeholder model id `CONFIGURE_VERIFIED_IMAGE_MODEL` is copied through.

## Contract examples

- `drone-vision-decision.json` is accepted. It opens `target-001` and a hold proposal. The image direction `center` is recorded as image space.
- `dog-vision-decision.json` updates `target-001` when that track is current. `switch_to_dog_vision` does not create a proposal.
- `ai-to-drone-proposal.json` is the key set for a stored proposal. It is not sent, and this card does not copy its reposition/left values onto the hold decision.

## Extra edge cases

- Confidence `0.01` still opens a track and still sets `motion_authorized` false.
- A detection that already carries `target-777` opens that id. The same decision does not replace an existing `target-001`.
- A second `drone_search` with a null track id updates the current track instead of allocating another id.
- Two people return review. With `staged_association` and exactly one detection on the current track, that track updates.
- `simulated: "true"` and a string confidence are rejected. No string is coerced to a boolean or a score.
- Labels `weapon`, `intent`, and `name` are rejected.
- A payload field `sdk_command` is an unknown-field rejection. A reason that is only `takeoff`, `rc 0 0 0 0`, or `move five meters` is rejected.
- A late decision and an older camera epoch leave the track and the kernel halt latch unchanged.
- A calibrated reposition becomes a proposal whose action is `reposition`, with an empty motion trace and no device call.

## Limitations

- This machine has CPython 3.12.10 only. Mypy checks with `python_version = 3.11`.
- The v2 slot is not registered. Wiring this provider in as `feature.dog_frame` would be wrong for the retired phone-incident workflow; nothing in Tasks 01–10 calls this factory for that slot. Gate C should switch the manifest to `feature.v2_vision_decision` / `ground-task-v2` when the loader admits it.
- Dog-stage decisions never emit a proposal. Task 23 owns dog commands, and Task 25 owns the camera handoff.
- `continue_homing` does not become a step. This card does not invent motion.
- Beacon epoch and map epoch stay null. They are not inferred from a box.
- Image left/right is not converted to a body yaw, and a box is not converted to meters.
- Nothing here calls xAI, measures inference latency, or shows that a later approval task will refuse the stored proposal.
