## Behavior

A batch is the active drone track, the current camera epoch, an observation time, and dog `vision.decision` messages correlated to frames. `dog_acquire` and `dog_approach` on the dog front camera can count. A downward camera, a `drone-` frame id, or a `drone/` camera frame id does not count. The model’s `suggested_action`, including `switch_to_dog_vision`, is not permission to switch.

`person_visible` with exactly one person box for the active track is one hit. The default threshold is two fresh hits inside 3000 ms. One hit stays `rssi` / `acquiring`. Two fresh hits set mode `visual`, `rssi_role` `supporting`, and record the frame ids. RSSI windows are copied through. They are not deleted and no new RSSI selection is emitted.

`not_visible` and `uncertain` clear the streak and stay on RSSI when homing is allowed. If homing is not allowed, that miss returns `review`. A mismatched track, a null track id, or more than one box returns `review` and does not hand off. A stale or future frame clears the streak. A wrong camera epoch, a drone frame used as the only input, or a non-dog stage is a typed rejection. A repeated frame id does not become a second hit.

The result never carries a dog command, a proximity goal, or an arrival. The handoff is a `decision_received` event whose payload says `dog_vision_handoff`. The v1 event allowlist has no separate handoff kind, and `state_changed` would require a frozen phase name. The proposed journal message is `mission.event`. Its `outcome` is null because that enum has no `visual` value; the mode is in `details.mode`. `details` also copies `message_id`, `mission_id`, `epoch`, `request_id`, `frame_id`, `track_id`, `beacon_epoch`, `map_epoch`, and `camera_epoch`.

Message kinds read: `vision.request`, `vision.decision`, `rssi.window`. Message kind proposed: `mission.event` / `dog_vision_handoff`.

## Extra edge cases

- The contract example is one fresh dog hit. `switch_to_dog_vision` on that single decision stays `acquiring`.
- `dog_approach` on the dog front camera counts as a dog hit. `drone_search` does not.
- A drone frame between two dog hits does not count and does not clear the dog streak. The handoff frame ids stay the dog frames.
- `uncertain` clears the streak the same way `not_visible` does.
- An empty detection list clears the streak and is not a switch.
- Repeating one frame id does not satisfy the threshold.
- A string `"true"` for `homing_allowed` is rejected. An unordered box is rejected.
- A cancelled or stale ticket does not hand off. The state double accepts the `decision_received` event and does not mark arrival or `DONE`.
- After the switch, the Pi RSSI window is still in the result and its median is unchanged.

## Limitations

- This machine has CPython 3.12.10 only. Mypy uses `python_version = 3.11`.
- `python -m patrol.ground.sim --task 25` cannot load the manifest until Gate C accepts `ground-task-v2`. The provider tests call `create(services)` directly, which is the acceptance path in the task card.
- A `review` decision latches review for the rest of that batch, so a later fresh hit in the same batch does not restart the streak.
- Two boxes go to review even when both boxes carry the active track id. A hit is exactly one matching box.
- A drone frame is ignored when dog hits are also present. It is a rejection only when the batch never sees the dog front camera.
- `person_visible` with an empty detection list clears the streak. The card only required that an empty list not switch modes.
- Nothing here sees a real person, a real Go2 frame, or a real RSSI window. Freshness is the difference between the fixture observation time and `captured_at`, not a camera timestamp measured on the dog.
- Approach commands stay with Task 23. Proximity stays with Task 26. This result does not declare either.
